# Assessment attachment migration 53: private release gate

This runbook describes the fixed release path; it does not itself authorize production operations. Execute it only within an authorized release. Migration 53 is required before releasing application code that depends on assessment attachment bindings. The existing 50–52 executor and its three receipts remain unchanged.

## Local review and rehearsal

- Complete the repository's Graphify and local verification gates on the final reviewed source. Review `20261105030000_exam_attachment_bindings.sql`, its Azure-transformed bytes, attachment ownership and stored-history behavior. Review the source and transformed SHA-256 values in the plan; the executor executes only that one transformed migration, never the 49 bootstrap files or `npm run migrate`.
- On a disposable, socket-only native PostgreSQL 17 installation, run `STUDIO_POSTGRES_BIN=<existing-local-bin> node scripts/azure-core/rehearse-forward-53.mjs`. The script requires an already installed binary, creates and removes its own local cluster, and rejects nonlocal target assumptions. Its output is **local, uncommitted rehearsal evidence**. It exercises the actual 49-file baseline, V1 expansion and activation, a failing 53 transaction, role/receipt preservation, non-file save and old nine-argument finalize, manual grading, unchanged historical attachment JSON and idempotent replay. It does not establish hosted compatibility or deployment readiness.
- Verify the actual target through an independently authorized read-only private-network probe. Confirm PostgreSQL 17, the import ledger state/digest, all three V1 receipt hashes and activation deployment SHA, protected built-in roles, V1 schema/RPC permissions, and absence of partial 53 objects. The fixed executor rejects mismatch or ambiguous state; do not repair its ledgers by hand or infer success from a filename alone.

## Future private-network execution

The existing manual private job now has two additional, separate actions: `forward-53-plan` and `forward-53-apply`. V1 `--forward` archives remain fixed at52 and cannot dispatch53. The dedicated `--forward-53` archive contains the exact1–53 schema inputs for hash inspection, but its executor applies only53. It includes a locked `pg` JavaScript dependency closure, no snapshot/import executor and no dependency download inside the container. Never run the original schema/import action on the populated database or expose the database publicly.

The bounded `forward-53.mjs` executor is transport-independent for local rehearsal. Its read-only plan verifies the expected imported baseline and all three prior V1 receipts; its apply rechecks the reviewed plan under the existing advisory lock and role/ledger locks, applies only 53, and stores a separate private receipt atomically. It compares the binary permission arrays of all roles, verifies 53 table/RLS/privilege, guarded-function and trigger postconditions, and sends the transactional PostgREST reload notification. A matching receipt and intact postconditions produce a no-op; partial or mismatched state requires investigation, not blind replay. The import ledger and V1 receipts are never rewritten.

For a future authorized plan, the fixed private evidence file `build/azure-core/private/forward-53-v1-evidence.json` contains `{ "verified": true, "activationSha": "<40-character independently verified V1 activation deployment SHA>" }`. That flag and SHA are an operator attestation, not an independent deployment probe. The fixed CLI accepts only `plan` and `apply`; apply reads `build/azure-core/private/forward-53-plan.json` and rejects missing, dirty or changed committed source/commit/tree before constructing a database client. Reinspect exact V1/53 state and obtain a fresh read-only plan after any ambiguous outcome.

The local CLI still uses actual clean Git commit/tree checks. The container has no Git checkout: its fixed job entrypoint instead verifies the packaged source/dependency hashes and committed-source attestation. Local prepare/start recheck the clean checkout, exact artifact metadata and current job image, command, bootstrap and allowed environment. The trusted inline bootstrap validates the manifest and every executable/dependency byte before importing packaged code or fetching the administrator URI. This is a reviewed artifact attestation, not independent proof of Git history or deployment readiness.

## Authorized execution order

Finish all local source/configuration/test/doc edits, Graphify refresh/check and the full local verifier. Review and commit the exact tree first; `--prepare` and `--start` refuse dirty or mismatched source before Azure calls. Keep `forward-53-v1-evidence.json` mode0600 and preserve its exact bytes between plan and apply. If a previous fixed `forward-53-plan.json` belongs to another commit, retain it privately under a distinct archival name before building the initial plan package; never edit its recorded hashes to make it match.

1. Build the first package with no reviewed plan: `node infra/azure-core/migration/package.mjs --forward-53`. Run `node infra/azure-core/migration/verify-package.mjs` for offline decryption/relocation validation. Both are local-only; no DB connection or cloud call is opened.
2. Prepare the existing manual private job: `node infra/azure-core/migration/deploy.mjs --prepare --forward-53-plan`. This publishes the encrypted artifact/key and configures the fixed job, but does not start it. Then run `--start --forward-53-plan`. Check the actual execution status and obtain `--receipt --forward-53-plan`; a successful start is not a successful plan.
3. Inspect `build/azure-core/hosted-forward-53-plan.json`: exact imported baseline, V1 receipt/activation hashes, protected roles, role byte digest/count, fixed53 source/transformed hashes, clean source commit/tree, absence of partial53 state and action `apply` or committed-provenance `noop`. The receipt binds the exact encrypted package SHA, source-manifest SHA and stable package-content SHA. Keep the selected job parameters and receipt privately. Copy the complete validated receipt, including transport metadata, into `build/azure-core/private/forward-53-plan.json` after review.
4. Rebuild with the same `--forward-53` package command and run offline verification again. The stable content digest (source, evidence and locked dependency bytes) must match the plan package. The reviewed-plan byte digest is added separately; encrypted and source-manifest hashes change. Source/evidence/vendor changes require a fresh read-only plan, not a forced apply.
5. Prepare/start/obtain the receipt using `--forward-53-apply`. The action revalidates package/plan/source before credentials and the database plan under the existing transaction/advisory/role/ledger locks. Its immutable success receipt is tied to this apply artifact and action. Any timeout, failure, missing receipt or ambiguous outcome requires read-only inspection and a fresh plan before another write; never infer rollback from a missing upload receipt.
6. Reuse the exact apply artifact for another `--prepare --forward-53-plan`, start and receipt. Require `noop`, matching53 committed receipt/source hashes, unchanged V1 receipts and role byte digest, and full schema/RLS/ACL/trigger postconditions. Independently check actual PostgREST schema-cache visibility after the transactional reload notification. Do not treat SQL commit alone as cache visibility.
7. Only after schema/cache acceptance merge the reviewed application tree, because the main workflow automatically deploys. Verify the actual production deployment is READY and bound to the real merge SHA/tree and canonical alias. Perform authorized read-only/public smoke checks separately. Hosted provider/file writes, concurrency and performance remain separate evidence boundaries.

Every prepared run has a distinct action+encrypted-SHA+timestamp+UUID receipt name. Uploads use create-if-absent; a reused receipt destination cannot replace earlier evidence. `--receipt` validates action, filename, encrypted/source-manifest/content hashes and committed source against the selected local package. Plan/apply packages are not interchangeable with V1, bootstrap, cutover or probe modes.

After a separately authorized private-network application, retrieve the immutable execution receipt; independently verify schema-cache visibility, functions, grants and actual exam/quiz save, upload and review behavior before deploying or enabling dependent features. Local checks do not prove the hosted outcome, upload/storage behavior, capacity or billing.

## Recovery and rollback

Migration 53 is additive and forward-only. Do not drop its tables, triggers, bindings or receipts, replay old migrations, or rewrite historical answers as a rollback. The native rehearsal must establish that pre-existing non-file work and unchanged legacy attachment references remain usable by the old application, but that is not a hosted guarantee. Once new 53-bound attachment writes exist, rolling back to application code that cannot understand or preserve them requires an explicitly reviewed compatible application revision and data/recovery plan; never assume older code or a frozen prior source contains new writes.
