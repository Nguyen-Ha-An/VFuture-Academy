# Academy database ownership and future cutover

This extraction prepares source and an independent schema; it does not provision a Supabase project or move live data. The user explicitly deferred new Database/Auth project creation. Academy's intended backend is a separate future Supabase project. Central retains no backend implementation after the split, and Competition owns a different future project.

`supabase/migrations/` contains Academy's unchanged inherited identity, authorization, member/branch/role, content/review, media, learning/progress/assessment, reporting, profile/certificate, notebook, MCP access and security migrations. The source's eight `20261014*_competition_*.sql` files are intentionally absent. The additional forward `20261023120729_preserve_shared_content_destinations.sql` migration corrects shared read-only inventory destinations without changing historical SQL or live data. It is validated only in disposable local databases. Keep the existing filenames and immutable SQL; execute the lexical ledger on a fresh target with `npm run migrate`. The script records exact filenames in `public.schema_migrations` and skips recorded files. Do not renumber migrations to fill gaps.

Fresh bootstrap and existing-data cutover are different operations. A new empty project needs the migration chain, private Storage buckets, Auth providers, site/redirect settings, OAuth server/client configuration, independent secrets and first authorized administrator. Do not seed production fixtures to create an administrator; use the reviewed role-grant workflow for an operator-selected account. Existing production data cannot be copied by merely replaying schema migrations.

A future authorized data migration must inventory Academy-owned tables and their foreign keys; preserve user IDs or maintain an audited mapping across Auth users/profiles/enrollments/progress/attempts/submissions/grades/certificates/projects/media; export only the approved dataset to encrypted operator storage; migrate Storage objects and metadata with appropriate owner/path mappings; and validate counts, constraints, authorization, content versions, completion evidence and signed downloads. Keep all exports, credentials and user records outside Git. Auth configuration/provider secrets, OAuth registrations, cookie/session continuity and token revocation require their own cutover decisions. Do not assume existing sessions or MCP grants work in the new project.

The old production project and its migration ledger remain untouched. Source exclusion of Competition SQL does not authorize removing Competition objects or migration records from an existing database. Do not aim `migrate` at the old shared production project to perform the extraction. Any later cutover needs an approved backup/restore plan and measured rehearsal before routing production traffic.

Recheck platform documentation when provisioning is authorized.
