# Academy Azure identity contract

This implementation is dormant while both backend selectors are absent or set to `supabase`. Azure requires `ACADEMY_BACKEND=azure` and `NEXT_PUBLIC_ACADEMY_BACKEND=azure` together. Set the public selector at build time and rebuild before cutover. A disagreement fails closed. This source implementation is not evidence of a configured customer tenant, direct Google client, delivered email, or a successful hosted login.

## Configuration

| Variable | Contract |
| --- | --- |
| `ENTRA_TENANT_ID` | Customer tenant UUID; never `common`, `organizations`, or the grant subscription tenant by assumption. |
| `ENTRA_CLIENT_ID` | Web application UUID in that customer tenant. |
| `ENTRA_CLIENT_SECRET` | Confidential web application credential, server-only; record its actual policy-permitted expiry separately. |
| `ENTRA_AUTHORITY` | HTTPS tenant-specific v2.0 authority, without a trailing slash. Discovery is loaded from `/.well-known/openid-configuration` below this path. |
| `ENTRA_ISSUER` | Exact issuer returned by the reviewed tenant discovery document. No wildcard or template issuer. |
| `ENTRA_SESSION_ENCRYPTION_KEY` | Base64 encoding of 32 cryptographically random bytes, stored as a server-only secret. Separate from the PostgREST signing secret. |
| `ENTRA_SESSION_MAX_AGE_SECONDS` | Optional absolute application-session bound, 3600–2592000 seconds; default 2592000 (30 days). Provider ID-token expiry is still enforced and refreshed independently. |
| `GOOGLE_CLIENT_ID` | Direct Google Web OAuth client ID; server-side configuration. Its authorized redirect URI is the canonical Academy `/auth/callback`. |
| `GOOGLE_CLIENT_SECRET` | Direct Google Web client credential, server-only. Never expose it through a `NEXT_PUBLIC_` variable or check in downloaded client JSON. |
| `ENTRA_GOOGLE_DOMAIN_HINT` | Legacy CIAM federation compatibility only. Direct Google login does not consult this setting. |
| `ENTRA_ADMIN_CLIENT_ID` / `ENTRA_ADMIN_CLIENT_SECRET` | Existing separate customer-directory administration app in the pinned Academy customer tenant. Its existing `User.ReadWrite.All` grant supports immutable Google binding reads and new federated-customer creation; no additional Graph permission or directory administrator role is requested. |
| `MICROSOFT_ENTRA_TENANT_ID` | Required for internal Microsoft sign-in; must equal approved workforce tenant `157419c9-2de9-45e7-a6f9-91546dbef629`. Other tenants, personal accounts and `common` are rejected. |
| `MICROSOFT_ENTRA_CLIENT_ID` | Separate, single-tenant workforce application UUID. Must differ from `ENTRA_CLIENT_ID`. |
| `MICROSOFT_ENTRA_CLIENT_SECRET` | Confidential workforce application credential, server-only. |
| `NEXT_PUBLIC_APP_URL` | Canonical HTTPS application origin. Local development permits HTTP only on localhost. |

Register exactly `NEXT_PUBLIC_APP_URL` + `/auth/callback` as the Web redirect URI on the Google Web client and the separate workforce application. Register `/login` as the workforce post-logout redirect URI. Direct Google login requests only `openid profile email`, with authorization code, state, nonce, PKCE S256, `access_type=offline` and `prompt=select_account consent`. It opens Google's authorization endpoint directly and returns to Academy; the CIAM user flow and its Add details page are outside this path.

Email/password continues to use Entra Native Authentication. Keep the customer application's public-client/Native Authentication capabilities, basic OIDC consent and required signed `oid` claim. Native requests use `openid profile email offline_access`. Existing Entra Web callback URIs and API permissions remain available for earlier confidential sessions; direct Google adds no Google API scopes or Graph permissions.

Google discovery must return the exact issuer `https://accounts.google.com`, authorization endpoint `https://accounts.google.com/o/oauth2/v2/auth`, token endpoint `https://oauth2.googleapis.com/token` and signing-key endpoint `https://www.googleapis.com/oauth2/v3/certs`. Endpoint substitutions fail closed. Google tokens use a distinct identity type and are verified with RS256, trusted keys, Google issuer, this client audience/authorized presenter, expiry/issuance bounds, immutable numeric subject and boolean `email_verified=true`; callback tokens must also match the transaction nonce. Signed `name`, `given_name` and `family_name` supply the profile name. Google does not guarantee a name claim: the Academy name-only fallback remains necessary when it is absent, without sending the learner through CIAM. Google's [OpenID Connect documentation](https://developers.google.com/identity/openid-connect/openid-connect) describes these claims and refresh-token consent behavior.

Email/password login, signup verification and password recovery run inline through same-origin `POST /api/v1/public/auth/native`. Passwords and verification codes pass over the server's HTTPS back channel to the documented native API and are never persisted or logged. ID/refresh tokens remain server-only. The server verifies signature, exact issuer, tenant, audience and lifetime before issuing the existing opaque HttpOnly session. Successful native signup OTP verification supplies explicit email-verification evidence; an absent `email_verified` claim is not otherwise treated as true. Existing email collisions still refuse automatic linking.

Continuation payloads are encrypted with attempt/handle/browser binding, expire after ten minutes, and use the existing atomic transaction RPC. A separate HttpOnly proof cookie per attempt isolates tabs; continuation responses never overwrite newer proof cookies. The browser receives only non-authenticating IDs and UI steps. Cross-origin or non-JSON requests, oversized input and attempts beyond the shared rate limit fail before provider access. Unsupported redirect challenges fail inline instead of opening a Microsoft password page.

Native refresh credentials carry an encrypted version marker so the worker uses public-client refresh without a client secret. Existing confidential OAuth/workforce refresh retain their original credentials and lease/version fencing. Registered email MFA follows introspection and method selection before an OTP challenge; SMS-only or registration-required methods are not enabled by this change. Recovery normalizes account-existence metadata and respects provider polling intervals and pending states. It signs out the requesting browser; immediate all-device Academy session revocation remains outside this change. Other existing sessions retain their previous provider-token expiry/refresh boundary.

Direct Google and inline email/password are normal public sign-in options. Google has no application-level email-domain restriction. Microsoft is a separate internal staff flow, not an External ID federation option. Register its application in the approved workforce tenant as single-tenant (`AzureADMyOrg`) with the same `/auth/callback` Web redirect URI. Its authority and exact issuer are pinned to `https://login.microsoftonline.com/157419c9-2de9-45e7-a6f9-91546dbef629/v2.0`; there is no configurable common authority. Discovery/JWKS/token/logout endpoints must remain on `https://login.microsoftonline.com`. The login transaction records the chosen provider and, for direct Google, the `google-v1` transaction kind server-side; callback query parameters cannot change them.

Microsoft documents [customer authentication methods and federation hints](https://learn.microsoft.com/en-us/entra/external-id/customers/concept-authentication-methods-customers), [tenant-specific issuer validation](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens#validate-the-issuer), and [customer password reset](https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-enable-password-reset-customers).

## Popup interaction

Only Google and internal Microsoft open a named popup directly inside the user's click handler. Credentials, signup and recovery use the inline Academy form. The parent stays on its current page if opening is blocked, sign-in is cancelled, the session cannot be verified, or the attempt expires; it never falls back to a top-level provider redirect. Buttons expose pending status and explicit cancellation. The legacy Supabase Google/Microsoft buttons use the same popup controller, while existing direct password forms remain available.

Each popup gets a cryptographically random, non-authenticating 192-bit correlation ID. Azure stores it inside the browser-bound, one-use login transaction. The callback ignores caller-supplied completion IDs and sets the HttpOnly session cookie before sending the popup to the same-origin completion page. Legacy Supabase uses server-generated PKCE plus a signed HttpOnly popup-context cookie; its authorization code remains single-use and the display context is consumed on callback. Callback responses never clear shared current-attempt cookies, because an older response may arrive after a retry. Azure consumes its database transaction and retains the login cookie until rotation, logout or its ten-minute expiry. Legacy display-context consumption clears only a marker keyed by the validated state; a new start supersedes the old marker. A stale or bogus callback cannot delete the newer attempt’s cookie.

Completion messages contain only an outcome and correlation ID. The parent requires the exact application origin, original window reference and current attempt for `postMessage`. An attempt-specific same-origin `BroadcastChannel` handles providers whose COOP policy removes `window.opener`; stale attempts cannot complete a new one. The parent independently calls the protected session endpoint before navigating through onboarding to the sanitized return path. It does not treat an existing session, a closed window, or an unmatched message as completion.

A popup closes after a matching parent acknowledgement. With no listening opener/channel, it leaves instructions to return to Academy manually. A window that appears closed may have been isolated by a provider, so its matching channel remains available while the parent offers retry. Authentication pages alone use `Cross-Origin-Opener-Policy: same-origin-allow-popups`; notebook isolation and the application CSP remain intact.

Local real-browser contracts are isolated from hosted services and credentials:

```
npx playwright test --config tests/e2e/auth-popup.config.ts
```

They exercise the production popup controller/completion code with a simulated local provider and session endpoint, including provider COOP, cancellation, blocked windows and stale completion with a pre-existing session. They do not establish hosted Google/Microsoft consent or cookie behavior.

## Identity mapping and migration

`academy_identity.mappings` maps the verified Entra `(issuer, oid)` pair to the existing Academy `users.id` UUID. Using `oid` avoids pairwise Entra `sub` differences between web and MCP token audiences. `findIdentityUser(issuer, objectId)` is read-only and never provisions users. Native External ID registration calls `resolveIdentityUser` only after server-side signature, issuer, tenant, audience and lifetime validation, with browser-bound back-channel and one-use continuation state. Earlier confidential Entra OAuth callbacks also require their transaction nonce.

Direct Google has an explicit two-step binding: verified Google `sub` → exact Entra federated identity (`signInType=federated`, `issuer=google.com`, `issuerAssignedId=sub`) → Entra object UUID → existing Academy mapping. Google claims are never presented as Entra-signed claims. The Graph adapter requires an enabled directory account, a valid object UUID and exactly one returned immutable binding, and rejects ambiguous/paginated results. Existing bindings win even when the Google email changes. For a genuinely new subject, callback processing may create an enabled federated customer and then read back the exact binding; a matching directory email/local email identity is a collision signal and never a linking mechanism. The existing Academy resolver independently refuses collisions with an existing Academy email. Refresh only reads bindings and cannot create directory or Academy identities. Microsoft documents the immutable [objectIdentity issuer and issuerAssignedId contract](https://learn.microsoft.com/en-us/graph/api/resources/objectidentity?view=graph-rest-1.0).

Internal Microsoft callbacks instead call `findMicrosoftStaffUser`: a pre-existing exact workforce `(issuer, oid)` mapping and an active account with a current effective staff permission are mandatory. Eligibility uses the current `role_assignments` / `role_definitions` model through `authorization_has_permission`, including branch membership suspension; a bare role name or matching email cannot admit an account. Microsoft never provisions an Academy user, links by email, or grants a role. Session reads recheck this eligibility, so suspending the account or withdrawing staff permissions blocks an existing Microsoft session immediately.

Before migrating existing accounts, create/recover the intended external tenant accounts and import an operator-reviewed mapping of their Entra object IDs to existing Academy UUIDs. Review the identity manifest outside Git and reconcile it against the tenant. Existing mappings win even if email or display name changes. Disabled or deleted identities are rejected on lookup, session creation and session reads, and cannot be silently reprovisioned from their existing mapping. An unmatched verified email that collides with an existing Academy user fails closed; it never links accounts. Unverified email is discarded for new accounts. New native identities require explicit successful signup-OTP evidence or boolean Entra `email_verified=true`; new direct Google identities require boolean Google `email_verified=true`. Existing Academy rows with a null email keep their original UUID: the authenticated encrypted Google session envelope supplies the verified Google email to the server actor without rewriting or linking an identity by email. Hosted claim configuration and migration mapping are release gates.

Existing internal staff require an explicit reviewed workforce-object mapping in addition to any External ID mapping. The same internal UUID may have both mappings when the operator has verified ownership. This does not merge or auto-link identities.

Apply `schema.sql` after the transformed owned migrations using the schema builder. Only the server service role can call identity RPCs; learner tokens cannot read mappings, login transactions or encrypted refresh credentials. Application runtime reaches these RPCs over PostgREST, not a direct private PostgreSQL connection. New identity inserts retain the existing profile/account triggers. A verified Google name also repairs the known untouched `unknown` profile placeholder through a conditional service mutation, preserving the UUID and old profile URL alias; real edited names and handles remain protected. `/welcome` decides whether the name-only fallback is needed and preserves the validated return path.

## Sessions and recovery

The browser receives only random 256-bit HttpOnly, SameSite=Lax, host-only cookies (`__Host-` and Secure in production). Lax is necessary for the cross-site OIDC callback. Login transactions expire after ten minutes and are atomically consumed only with the matching browser cookie. Provider state, nonce and PKCE verifier are generated independently. Session identifiers are hashed in the database. A sign-in replaces and revokes the previous session.

Every authenticated server read checks database revocation and expiry. Provider ID-token expiry triggers refresh; an expired token is never accepted during a provider/storage outage. Refresh credentials are AES-256-GCM encrypted and bound to both the stored database provider and session hash. Database provider values remain `external-id` and `microsoft`; the direct Google protocol, client, original subject, verified email and display name are distinguished inside the authenticated encrypted `google-v1` envelope. This application marker is not an Entra token claim. Server actor reads can supply verified Google email/name from that envelope for legacy rows with missing metadata while retaining their mapped Academy UUID.

Entra refresh validates its exact issuer, tenant, audience, original pairwise subject and object ID. Encrypted `native-v1` credentials select public-client refresh without a client secret; earlier confidential Entra/workforce credentials retain their corresponding original application. Direct Google refresh selects the Google client from the authenticated envelope, verifies a fresh Google ID token for the same Google subject, rechecks the enabled exact directory binding, and requires the current active Academy mapping to return the original Academy UUID. Changed/reassigned mappings, disabled directory accounts and rejected Google grants cannot rotate the session. Refreshed verified Google email/name replace the session envelope metadata without email linking.

The refresh lease has a random owner token and a 45-second expiry; rotation, rejection-triggered revocation and release all check version, owner and unexpired lease. A losing instance polls for up to 9.5 seconds, with a ten-second total database-read deadline, for the owner to commit and reloads the updated session. A timeout reports temporary unavailability without revoking it. Provider relabeling cannot authenticate encrypted credentials. An expired or losing worker cannot rotate credentials, release a successor lease or delete its session, even before the successor commits. Transient network failures release the active lease without revoking it. A rejected grant revokes its session and requires sign-in. Absolute session expiry requires sign-in even after successful refresh; no provider token reaches the browser.

The absolute application-session expiry is fixed at login, shared by the cookie and stored session, and defaults to 30 days for native email, Google and Microsoft. Refresh never extends that expiry, including for sessions created under an earlier shorter bound.

Google consent is requested to obtain the app-held refresh grant. If Google nevertheless omits a refresh token, its encrypted profile envelope remains available only for the current ID-token lifetime; the session then revokes and requires sign-in. A successful callback alone does not establish 30-day session continuity. Prove a real Google refresh in hosted acceptance before claiming it.

POST logout checks browser origin, revokes the local session and clears cookies. Direct Google logout returns to Academy `/login` without calling CIAM or globally signing out the Google account. Native/legacy Entra and workforce logout may also redirect to their configured provider logout endpoint; its availability cannot prevent local revocation.

Authenticated learner and staff pages validate the server actor on mount and reuse a successful same-actor result in that mounted guard for five minutes. Focus and visible-tab events check again only after that window or an invalidation; skipped events never extend freshness. There is no periodic session polling, and losing focus does not conceal a recently validated workspace. A required check conceals prior content until server validation completes. Network, timeout and server failures invalidate freshness and show a bilingual retry state without navigation or cookie clearing; only a server-confirmed original actor can restore the mounted workspace. A 401 sends the visitor to sign-in with a sanitized current return path. A confirmed actor change stays concealed until a fresh authorized layout loads.

Cross-tab logout and login-change hints bypass freshness and invalidate in-flight checks; hints never establish authentication. Confirmed native, legacy email and popup login call notifyIdentityChanged() to notify other tabs. Rendered sign-out forms emit a non-authenticating logout hint; local revocation remains server-owned. Pending checks hide and disable the subtree and body portals while preserving same-actor drafts and editing focus/selection. Confirmed logout or actor change discards the previous actor tree. Freshness is only a UI optimization held in memory, not authority for API access. Server-side account and permission checks remain authoritative on every authenticated request. Without a browser identity hint, an idle open page can retain its rendered UI until the next stale focus/visibility check or navigation; API access still observes server revocation immediately.

Entra discovery and shared signing keys have bounded caches, coalesced fetches and five-second failure backoff. Direct Google discovery has a bounded five-minute cache and validates its complete endpoint allowlist. Expired cached material is never reused after a failed fetch. Signing-key rotation can take up to sixty seconds to become visible locally. Entra endpoints must stay on the configured authority's HTTPS origin; Google's separately pinned origins are listed above.

Key rotation requires an explicit plan: revoke existing session rows before replacing the encryption key, then require reauthentication. Do not copy refresh tokens, passwords, session cookies, state records or credentials into migration receipts, logs or Git.

## Local evidence and hosted gates

Focused tests cover signed-claim rejection, PKCE/navigation, encryption binding, immutable Google directory binding and collision refusal, preserved Academy UUIDs and legacy verified email, profile placeholder repair, refresh continuity/mapping rejection, browser-bound callbacks, local Google logout and legacy auth behavior. Run the PostgreSQL semantics suite with `PGLITE_MODULE_PATH` pointing to a local `@electric-sql/pglite` installation:

```
PGLITE_MODULE_PATH=/absolute/path/to/@electric-sql/pglite npx vitest run tests/scripts/azure-identity-schema.test.ts
```

Its default skip without that external runtime is not a passed release gate. The suite checks one-use state, preserved UUIDs, refusal to auto-link emails, profile creation, session revocation/version checks, lease-owner and expiry fencing, and learner ACL denial. Independent-worker promise interleaving tests hold a successful refresh before its database commit while a second worker attempts refresh; only the lease owner redeems the grant. It does not establish simultaneous hosted transactions, network behavior, tenant claim configuration, password reset, direct Google callback/client configuration, federated-customer creation, branded email delivery or long-exam continuity. Complete Graphify and the full repository local verifier for the final source tree, then separately prove hosted callback, existing-account UUID preservation, disposable Google-user provisioning, verified email/name delivery, refresh, revocation, native signup/recovery and workforce eligibility before release claims.

## Google visible branding

Direct Google uses the canonical Academy `/auth/callback` registered on its Google Web client, so CIAM is not the Google callback host. Google app-name/logo display and verification remain separate Google Console configuration/review concerns. Direct callback ownership and successful authentication do not prove approved Google branding.
